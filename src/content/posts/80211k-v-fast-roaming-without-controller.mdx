**Scope:** This article focuses on controllerless Wi-Fi roaming using **802.11k and 802.11v**. 802.11k provides neighboring AP information to help the client discover suitable candidates, while 802.11v provides mechanisms such as BSS Transition Management that allow the network to recommend candidate APs. The final roaming decision remains with the client.

## What Is Wi-Fi Roaming?

Wi-Fi roaming is the process by which a wireless client moves its connection from one access point to another on the same network — ideally without dropping active sessions. In a home or office with multiple APs serving the same SSID, a client should seamlessly transition to a stronger AP as it moves through the space.

Without intervention, clients hold onto their current AP until the signal is barely usable, then disconnect and re-associate — causing a hard handoff with packet loss. For voice and video calls, this means dropped conversations.

The 802.11k/v standards solve this by giving APs the ability to *help* clients make better roaming decisions — without a central controller orchestrating everything.

## The Problem

You deploy two APs — AP-A and AP-B — on the same SSID. A client associates to AP-A with strong signal. The client walks toward AP-B. RSSI drops. Without intervention, the client holds onto AP-A until it's barely usable, then disconnects and re-associates — causing a hard handoff with packet loss.

The goal: detect the weak signal early, find a better AP, and *suggest* the roam before the client is desperate.

<Callout type="note" title="Same SSID, same network">
For roaming to work, all APs must broadcast the **same SSID** with the **same password and authentication method**. The client sees them as a single network — it doesn't know (or care) which physical AP it's connected to. This is what makes seamless roaming possible.
</Callout>

## What Does "Controllerless" Mean?

In enterprise Wi-Fi, a **Wireless LAN Controller (WLC)** centrally manages all APs — deciding when clients should roam and to which AP. It has a complete view of every client, every AP, and every RSSI reading.

**Controllerless** means there's no central authority. Each AP runs its own roaming daemon, and APs coordinate peer-to-peer through multicast messaging. There's no single point of failure, no controller license fee, and no bottleneck — but each AP must make local decisions with only its own view of the network.

This architecture works well for small to medium deployments (2–20 APs) where the overhead of a controller isn't justified.

## 802.11k and 802.11v at a Glance

| | **802.11k** | **802.11v** |
|---|---|---|
| **Purpose** | Neighbor discovery — tells the client which APs are nearby | BSS Transition Management — recommends a specific AP to roam to |
| **How it works** | AP provides a Neighbor Report listing nearby APs, channels, and BSSIDs | AP sends a BTM Request suggesting a target AP |
| **Who acts** | Client uses the report to narrow its scan channels | Client decides whether to accept the recommendation |
| **Forced?** | No — client can ignore the report | No — client can accept, reject, or ignore |
| **Key benefit** | Faster scanning (client doesn't probe all channels) | Fewer probe storms, more controlled roaming |

<Callout type="tip" title="The client always decides">
Both 802.11k and 802.11v are *advisory* protocols. The AP can suggest, recommend, and even disassociate a stubborn client — but the final roaming decision always belongs to the client device.
</Callout>

## Architecture Overview

Each AP runs a roaming daemon as a single process with three threads:

| Thread | Role |
|---|---|
| **Event loop** | Handles kernel events — link status, IP changes, driver RSSI/association events |
| **Timer thread** | 1 Hz tick — manages roam timers, sends multicast probes, runs periodic site surveys |
| **Peer listener** | Receives PROBE_REQ / PROBE_RESP from peer APs on multicast `239.1.1.100:9001` |

Two shared tables coordinate everything:

- **Roam Table** — tracks per-station RSSI, roam state, and candidate info
- **Activity Table** — tracks per-station idle state and keepalive counters

All three threads read and write these tables under mutex. That's how they coordinate — no message queues, no inter-process communication. Just shared state with locks.

Let's walk through each phase.

## Phase 1: Detect

Roaming starts when a client's RSSI drops below the configured threshold. The driver reports the station's current RSSI through a kernel event.

<Callout type="note" title="Threshold">
The roam-trigger threshold is configurable per band — typically −70 dBm for both 2.4G and 5G. The AP compares the reported RSSI against this threshold to decide whether to start looking for a better candidate.
</Callout>

Three gate checks happen before a probe is armed:

1. **3-second rate limit** — skip if this station was handled less than 3 seconds ago
2. **RSSI threshold** — station's signal is below the configured threshold → proceed
3. **Arm countdown** — start a 2-second countdown before sending the probe

Only **associated** station events can arm a probe. Un-associated events (a station heard on air but not connected to this AP) only update the Roam Table — they never trigger a roam.

<Callout type="tip" title="Why associated only?">
If every heard probe triggered a roam attempt, the AP would flood the network with requests for stations it doesn't even serve. Only stations actually connected to this AP are worth steering.
</Callout>

## Phase 2: Discover

Once the countdown reaches zero, AP-A sends a **multicast PROBE Request** to `239.1.1.100:9001`. Every peer AP on the same roaming group receives it.

The probe contains:
- **Client MAC** — the station we want a better AP for
- **Sender MAC** — this AP's MAC
- **Radio ID / WLAN ID** — which radio the station is on
- **RSSI** — this AP's view of the client's signal
- **SSID** — so peers can check they serve the same network

Each peer AP evaluates the probe against four gates:

| Gate | Check | Fail = |
|---|---|---|
| SSID match | Peer serves the same SSID | No response |
| Known station | Peer has this MAC in its Roam Table | No response |
| Recency | Peer saw this station within the last 5 seconds | No response |
| RSSI margin | Peer's RSSI for this station ≥ AP-A's RSSI + 10 dB | No response |

<Callout type="tip" title="Why the 10 dB margin?">
A peer only responds if it has a *meaningfully* better signal for the client. This prevents unnecessary roams — if the peer's signal is only 2 dB stronger, the client is better off staying put.
</Callout>

If all gates pass, the peer sends a **unicast PROBE Response** back to AP-A with its own RSSI for that client.

## Phase 3: Decide

AP-A waits for the candidate window to close — roughly 2 seconds. During this window, it collects all peer responses.

The decision logic is straightforward:

**The strongest PROBE Response wins.** AP-A keeps only the best candidate — highest RSSI from a peer — and discards everything weaker.

If no peer responded, or no response had sufficient RSSI margin, no candidate is selected and the roam doesn't happen. The client continues on AP-A.

<Callout type="note" title="Candidate selection">
The winning candidate's info — channel, RSSI, and target BSSID — is stored for the steering phase. Only the single best candidate moves forward.
</Callout>

## Phase 4: Steer

With a candidate selected and the cooldown clear (last BTM was more than 29 seconds ago), AP-A executes the steering step.

AP-A builds a **Neighbor Report IE** (Element ID 52) naming the candidate AP's BSSID and channel, then constructs a **BSS Transition Management (BTM) Request** frame and sends it to the client.

The BTM frame tells the client: *"There's a better AP at this BSSID on this channel. You should roam."*

<Callout type="note" title="The client decides">
802.11v BTM is a *request*, not a command. The client can accept, reject, or ignore it. Some clients roam immediately. Some take 10 seconds. Some don't respond at all — in which case, if disassociation timing is enabled, AP-A disassociates the station after 20 seconds to force the issue.
</Callout>

If the client accepts and roams to the target AP, the new AP detects the association and resets its internal state. The cycle starts fresh.

<Callout type="note" title="Real-world example: VoIP call">
You're on a Teams call walking from your desk (near AP-A) to the conference room (near AP-B). Your phone's RSSI drops from −55 dBm to −72 dBm. AP-A detects this, probes AP-B, learns AP-B has you at −45 dBm, and sends a BTM request. Your phone roams in 120 ms — you never noticed. Without 802.11k/v, the phone would hold on until −80 dBm, disconnect, scan all channels, re-associate — dropping 1–2 seconds of audio.
</Callout>

## IP Lifecycle

One detail that's easy to overlook: how does the daemon handle IP changes?

The roaming daemon joins a multicast group (`239.1.1.100`) on the bridge interface. If the AP's IP changes — say, DHCP renews — the multicast membership breaks.

The daemon watches for address-change events from the kernel. When it sees a new address on the bridge, it leaves the old multicast group and rejoins under the new IP. No restart required.

This also handles the cold-boot case: if the bridge has no IP at daemon startup (DHCP hasn't completed yet), the daemon creates the multicast socket anyway, waits for an address, and joins once DHCP assigns one. Without this, the daemon would crash-loop until DHCP finished.

## What Clients Actually Do

Not all clients roam the same way:

| Client | Roaming behavior |
|---|---|
| **Android** | Roams reliably on BTM. Sometimes returns response code 7, but still roams. Auto-roam threshold around −70 to −75 dBm. |
| **iPhone** | Mixed strategy — sometimes auto-roams, sometimes uses 802.11k, sometimes BTM. BTM only fires if the peer has a probe entry for the station within the last 5 seconds. |
| **Linux** | Roams quickly — probes aggressively across all channels. |
| **Windows** | Same as Linux — aggressive channel probing. |

<Callout type="gotcha" title="iPhone caveat">
iPhone doesn't probe as broadly as Android or Linux. A neighboring AP may not have a recent probe from the iPhone, meaning it can't answer the multicast PROBE_REQ — so 802.11v BTM is less likely to trigger for iPhone clients. 802.11k and auto-roaming remain more reliable paths.
</Callout>

## Closing

Controllerless roaming works because each AP runs the same daemon, shares state through multicast, and follows the same decision logic. The cycle — detect, discover, decide, steer — repeats continuously. There's no central authority; coordination happens peer-to-peer.

The tradeoff is client behavior. Android and Linux probe aggressively, so peer APs learn about them quickly. iPhone is more conservative, which limits the effectiveness of the probe-based discovery path. For mixed-device environments, 802.11k neighbor reports and auto-roaming fill the gaps that BTM can't reach.

The result: **120–130 ms** from steering decision to first data packet on the new AP. No controller required.
